② train.py 만들기 — ml-train 폴더에 train.py 파일을 만들고 아래 코드를 붙여 넣습니다.

train.py

import json, pathlib
import pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.pipeline import Pipeline
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import f1_score, precision_score, recall_score
import joblib


ART = pathlib.Path("artifacts")
ART.mkdir(exist_ok=True)

df = pd.read_csv("seed.csv")

df["text"] = df["text"].astype(str)
X_train, X_test, y_train, y_test = train_test_split(
    df["text"], df["label"], test_size=0.2, random_state=42, stratify=df["label"]
)

# tfidf_ngram = (2, 5)
tfidf_ngram = (3, 6)
tfidf_min_df = 2
threshold = 0.5
model = Pipeline([
    ("tfidf", TfidfVectorizer(analyzer="char", ngram_range=tfidf_ngram, min_df=tfidf_min_df)),
    ("clf", LogisticRegression(max_iter=1000))
])

model.fit(X_train, y_train)

pred = model.predict(X_test)
metrics = {
    "f1": float(f1_score(y_test, pred)),
    "precision": float(precision_score(y_test, pred)),
    "recall": float(recall_score(y_test, pred)),
}

# 로컬 저장
joblib.dump(model, ART / "model.joblib")
(ART / "metrics.json").write_text(
    json.dumps(
        {**metrics, "n_train": int(len(X_train)), "n_test": int(len(X_test))},
        ensure_ascii=False, indent=2
    ),
    encoding="utf-8"
)

print("saved:", ART / "model.joblib")
print("metrics:", metrics)

모델 구성 요소

문자 n-gram CHAR N-GRAM

문장을 글자 단위 조각으로 쪼갠 것

  • “정말 불쾌한” → 정말 / 말 불 / 불쾌 / 정말 불 …
  • 형태소 분석기 없이도 조사·어미 변화에 어느 정도 대응
  • (3, 6)이면 3~6글자 조각을 모두 사용

TF-IDF TERM WEIGHTING

조각마다 “이 문장에서 얼마나 특징적인가”를 점수로 매김

  • 한 문장에 자주 나오면 점수 ↑
  • 거의 모든 문장에 나오는 조각은 점수 ↓
  • 결과는 문장 하나당 숫자 벡터 하나

로지스틱 회귀 LOGISTIC REGRESSION

벡터를 받아 “label 1일 확률”을 0~1 사이 값으로 출력하는 분류기

  • predict_proba → 확률 (예: 0.84)
  • predict → 확률이 0.5 이상이면 1, 아니면 0

서빙 코드 이해

model.joblib은 파일일 뿐이라 누가 문장을 보내 주지 않습니다. 그래서 모델을 불러 두고, 요청이 오면 예측해서 돌려주는 웹 서버(FastAPI)로 감쌉니다. 요청 하나가 처리되는 흐름은 다음과 같습니다.

app.py

# uvicorn app:app --host 0.0.0.0 --port 8088
import os
from contextlib import asynccontextmanager

import joblib
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel


MODEL_PATH = os.getenv("MODEL_PATH", "artifacts/model.joblib")

model = None


@asynccontextmanager
async def lifespan(app: FastAPI):
    global model
    model = joblib.load(MODEL_PATH)
    yield


app = FastAPI(title="toxicity-filter-test", lifespan=lifespan)


class Req(BaseModel):
    text: str


@app.get("/healthz")
def healthz():
    return {"ok": True}


@app.post("/predict")
def predict(req: Req):
    if not req.text or len(req.text) > 300:
        raise HTTPException(status_code=400, detail="text length must be 1..300")

    proba = float(model.predict_proba([req.text])[0][1])
    label = int(proba >= 0.5)
    return {"label": label, "toxic_proba": proba}
01

MODEL_PATH = os.getenv("MODEL_PATH", ...)

모델 파일 경로를 환경변수로 받고, 없으면 기본값을 씁니다. 나중에 컨테이너나 쿠버네티스에서 코드를 고치지 않고 경로만 바꿀 수 있습니다.

02

lifespan

서버가 켜질 때 yield 앞부분이 한 번 실행되어 모델을 전역 변수 model에 올립니다. 요청마다 파일을 읽으면 느리기 때문입니다. yield 뒤는 서버가 종료될 때 실행되는 구간인데, 여기서는 할 일이 없어 비워 둡니다.

03

class Req(BaseModel)

요청 본문의 형식입니다. text 문자열이 반드시 있어야 하고, 없거나 타입이 다르면 FastAPI가 알아서 422 오류를 돌려줍니다.

04

/healthz

서버가 살아 있는지 확인하는 용도입니다. 이후 쿠버네티스 헬스체크(probe)를 추가할 때 이 주소를 사용합니다.

05

if not req.text or len(req.text) > 300

빈 문자열이거나 300자를 넘으면 직접 400 오류를 냅니다. 학습 데이터가 짧은 한 줄 댓글이라 너무 긴 입력은 막아 둡니다.

06

model.predict_proba([req.text])[0][1]

문장을 리스트에 담아 넣으면 [[label 0 확률, label 1 확률]]이 나옵니다. 그중 label 1일 확률만 꺼냅니다. TF-IDF 전처리는 Pipeline 안에 들어 있어 원문 그대로 넣으면 됩니다.

07

label = int(proba >= 0.5)

확률이 0.5 이상이면 1로 판정합니다. 학습 파트에서 실험한 임계값(threshold)이 서빙에서는 바로 이 줄입니다.

왜 on_event("startup") 대신 lifespan을 쓰나요? 서버 시작 시 모델을 불러오는 코드를 @app.on_event("startup")로 쓰는 예제가 많지만, FastAPI 공식 문서에서는 이 방식을 더 이상 권장하지 않는(deprecated) 것으로 안내하고 lifespan 사용을 권장합니다. 이 교안은 lifespan을 씁니다.

EXPOSE는 “이 컨테이너는 8088을 쓴다”는 문서 역할이고, 실제 접속은 docker run -p로 엽니다. CMD는 컨테이너가 시작될 때 실행할 명령으로, 로컬에서 쓴 uvicorn 명령과 같습니다.

COPY 순서를 바꾸면? COPY app.py와 COPY artifacts/를 RUN pip install보다 위에 두면, 코드 한 줄이나 모델 파일만 바꿔도 그 아래의 설치 단계 캐시가 깨져 패키지를 매번 처음부터 다시 설치합니다. 결과 이미지는 같지만 빌드 시간이 크게 늘어납니다.
모델을 이미지에 넣으면 생기는 일. 가장 단순한 방식이지만, 모델을 다시 학습할 때마다 이미지를 새로 빌드하고 다시 배포해야 합니다. 이번 실습에서는 이 방식으로 진행하면서 그 불편함을 직접 느껴 봅니다.

빌드와 실행

BASH

docker build -t toxicity-filter:v260429v1 .
docker run --rm -p 8088:8088 toxicity-filter:v260429v1
  • -t toxicity-filter:v260429v1이미지 이름과 태그를 붙입니다. 태그는 v + 날짜(260429) + 순번(v1) 형식으로, 언제 만든 몇 번째 이미지인지 알아볼 수 있게 합니다.
  • --rm컨테이너가 종료되면 자동으로 삭제합니다. 테스트용 실행에서 종료된 컨테이너가 쌓이지 않게 합니다.
  • -p 8088:8088내 PC 포트:컨테이너 포트 순서입니다. 내 PC의 8088로 온 요청을 컨테이너의 8088로 보냅니다.

컨테이너가 터미널을 점유한 채 실행되므로, 새 터미널을 열어 호출합니다.

BASH — 새 터미널

curl localhost:8088/healthz
curl -X POST localhost:8088/predict \
  -H "Content-Type: application/json" \
  -d '{"text": "말이 너무 심하네요"}'

로컬 실행 때와 같은 응답이 나오면 성공입니다. 확인이 끝나면 컨테이너를 실행한 터미널에서 Ctrl+C로 종료합니다. --rm을 붙였으므로 컨테이너도 함께 삭제됩니다.

포트가 이미 사용 중이라는 오류가 나면 05장에서 띄운 로컬 uvicorn이 아직 8088을 쓰고 있는 것입니다. 해당 터미널에서 Ctrl+C로 종료한 뒤 다시 실행하세요.

컨테이너 안의 버전 확인

requirements.txt에 버전을 적지 않았으므로, 이미지를 빌드한 시점의 최신 버전이 설치됩니다. 학습할 때 쓴 scikit-learn과 같은지 반드시 확인합니다.

BASH

docker run --rm toxicity-filter:v260429v1 pip list

이미지 이름 뒤에 명령을 적으면 CMD 대신 그 명령이 실행됩니다. 출력에서 scikit-learn 줄을 찾아, 학습 환경에서 pip list로 메모해 둔 버전과 비교합니다. 이 교안을 작성한 시점에는 둘 다 1.9.1이었습니다.

버전이 다르면 어떻게 되나요? 모델을 불러올 때 InconsistentVersionWarning 경고가 나옵니다. 예를 들어 1.9.1로 학습한 모델을 1.8.0에서 불러오면 “Trying to unpickle estimator Pipeline from version 1.9.1 when using version 1.8.0. This might lead to breaking code or invalid results.”라는 경고가 나옵니다. 서버는 뜨지만 결과를 믿을 수 없게 됩니다. 08장에서 직접 재현해 봅니다.

Deployment와 Service 작성

하나의 파일에 ---로 구분해 두 리소스를 함께 적습니다. 서빙 리소스는 serving이라는 별도 namespace에 둡니다.

serving-basic.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: toxicity-filter
  namespace: serving
spec:
  replicas: 1
  selector:
    matchLabels:
      app: toxicity-filter
  template:
    metadata:
      labels:
        app: toxicity-filter
    spec:
      containers:
        - name: app
          image: toxicity-filter:v260429v1
          imagePullPolicy: Never
          ports:
            - containerPort: 8088
---
apiVersion: v1
kind: Service
metadata:
  name: toxicity-filter
  namespace: serving
spec:
  type: NodePort
  selector:
    app: toxicity-filter
  ports:
    - name: http
      port: 8088
      targetPort: 8088
      nodePort: 30089
01

namespace: serving

클러스터 안의 리소스를 용도별로 나누는 공간입니다. 이후 DB 같은 다른 구성 요소와 섞이지 않도록 서빙 리소스를 따로 모읍니다. namespace는 미리 만들어 두어야 하고, 조회할 때도 -n serving을 붙여야 합니다.

02

replicas: 1

Pod를 1개 띄웁니다. Pod가 죽으면 Deployment가 새로 만들어 개수를 유지합니다.

03

imagePullPolicy: Never

외부 저장소에서 받아오지 않고, 앞에서 import한 이미지만 쓰라는 뜻입니다.

04

containerPort: 8088 · targetPort: 8088

앱이 실제로 열고 있는 포트(Dockerfile의 --port 8088)와 같아야 합니다. 다르면 Pod는 Running인데 접속이 되지 않습니다.

05

selector ↔ labels

Service의 selector가 Pod의 labels(app: toxicity-filter)와 같아야 연결됩니다. 다르면 Service는 만들어져도 보낼 Pod가 하나도 없습니다.

06

nodePort: 30089

클러스터를 만들 때 로드밸런서에 열어 둔 30080-30089 범위 안의 값입니다. 범위를 벗어나면 내 PC에서 접속되지 않습니다.

배포와 접속 확인

BASH

k apply -f serving-basic.yaml

k get pods -n serving
k get svc -n serving

내 PC에서 보낸 요청이 Pod까지 가는 경로입니다. 포트 번호가 여러 군데에서 나오는 것에 주의합니다.

08 — TROUBLESHOOTING

장애 재현 실습

방금 배포한 서빙 환경을 일부러 망가뜨려 보며, 현장에서 마주치는 문제를 진단하는 연습을 합니다.

시나리오마다 흐름은 같습니다. 실무에서는 언제 생기는지, 재현, 증상 확인, 해결 순서입니다. 각 시나리오가 끝나면 원래 상태로 되돌린 뒤 다음으로 넘어갑니다.

시나리오 1 — 이미지를 찾지 못함

실무에서는 이미지 태그를 잘못 적거나, 이미지를 레지스트리에 올리지 않고 배포 YAML만 먼저 반영했을 때, 노드가 레지스트리에 접근할 권한이 없을 때 자주 발생합니다. 이번 실습 환경에서는 k3d image import를 빼먹은 경우가 가장 흔합니다.

BASH — 재현

k set image deployment/toxicity-filter app=toxicity-filter:v260429v9 -n serving
k get pods -n serving
k describe pod <새로 생긴 Pod 이름> -n serving

OUTPUT (예시) — k get pods -n serving

NAME                               READY   STATUS              RESTARTS   AGE
toxicity-filter-7c9d8b6f5d-4xk2p   1/1     Running             0          10m
toxicity-filter-5c4b7d9f8-abcde    0/1     ErrImageNeverPull   0          20s

describe의 Events에서 Container image "toxicity-filter:v260429v9" is not present with pull policy of Never 같은 메시지를 확인할 수 있습니다. imagePullPolicy: Never를 쓰지 않았다면 ErrImagePull → ImagePullBackOff로 보입니다.

BASH — 해결

k rollout undo deployment/toxicity-filter -n serving
k get pods -n serving
QUIZ

새 Pod가 실패하는 동안에도 curl localhost:30089/healthz는 계속 응답합니다. 왜일까요?

정답 보기
롤링 업데이트는 새 Pod가 Ready가 되기 전에는 기존 Pod를 내리지 않습니다. 이번에는 컨테이너가 아예 시작되지 못했으므로 새 Pod는 Ready가 될 수 없고, 기존 Pod가 그대로 요청을 받습니다. 다만 새 버전이 반영되지 않은 채 남아 있으므로, k rollout status로 배포 결과를 확인하는 습관이 필요합니다.

시나리오 2 — 모델 경로 오류로 계속 재시작

실무에서는 모델 파일을 볼륨으로 마운트하다 경로를 오타 내거나, 이미지를 빌드할 때 모델 파일 COPY를 빼먹거나, 설정값(환경변수)이 환경마다 다르게 들어갔을 때 발생합니다. 코드는 정상이어도 설정 한 줄 때문에 서버가 시작되자마자 죽습니다.

BASH — 재현

k set env deployment/toxicity-filter MODEL_PATH=/models/model.joblib -n serving
k get pods -n serving -w           # 상태가 바뀌는 것을 지켜봅니다 (종료: Ctrl+C)
k logs <실패한 Pod 이름> -n serving

새 Pod의 상태가 Error를 거쳐 CrashLoopBackOff로 바뀌고 RESTARTS 숫자가 늘어납니다. k logs 마지막 줄에는 FileNotFoundError: [Errno 2] No such file or directory: '/models/model.joblib'가 보입니다. lifespan에서 모델을 읽다가 실패하면 서버가 시작도 못 하고 종료되기 때문입니다. 재시작 간격은 10초, 20초, 40초처럼 점점 길어져 최대 5분까지 늘어납니다.

기존 Pod는 살아 있을까요? 시나리오 1과 달리, 이번에는 기존 Pod까지 내려가 서비스 전체가 끊길 수 있습니다. probe가 없으면 쿠버네티스는 “컨테이너가 실행 중이면 Ready”로 판단하는데, 새 컨테이너는 시작 직후 잠깐 실행 중이었다가 모델 로드에서 죽습니다. 그 짧은 순간에 Ready로 잡히면 롤링 업데이트가 성공한 줄 알고 기존 Pod를 내립니다. 타이밍에 따라 결과가 다르므로 직접 curl로 확인해 보세요. 이 문제를 막는 것이 readinessProbe입니다.

BASH — 해결

k rollout undo deployment/toxicity-filter -n serving
# 또는 환경변수를 올바른 값으로 되돌립니다
# k set env deployment/toxicity-filter MODEL_PATH=artifacts/model.joblib -n serving
QUIZ

시나리오 3 — 학습과 서빙의 scikit-learn 버전 불일치

실무에서는 학습은 개발자 노트북이나 노트북 서버에서 최신 버전으로 하고, 서빙 이미지는 몇 달 전에 만든 환경 그대로 쓰는 경우에 생깁니다. requirements.txt에 버전을 적지 않으면 이미지를 언제 빌드했느냐에 따라 설치되는 버전이 달라져서 더 쉽게 일어납니다. 에러 없이 서버가 뜨기 때문에 오랫동안 모르고 지나가기도 합니다.

BASH — 재현 (ml-serve 폴더의 가상환경에서)

pip install scikit-learn==1.8.0      # 학습 때보다 낮은 버전으로 되돌립니다
uvicorn app:app --host 0.0.0.0 --port 8088

서버 로그에 InconsistentVersionWarning: Trying to unpickle estimator Pipeline from version 1.9.1 when using version 1.8.0. This might lead to breaking code or invalid results.가 Pipeline, TfidfVectorizer, LogisticRegression 등 여러 번 나옵니다. 이 교안의 모델은 1.8.0에서도 같은 확률(0.840)을 냈지만, 버전 차이가 크면 결과가 달라지거나 오류가 날 수 있어 경고만 보고 넘어가면 안 됩니다.

BASH — 해결

pip install -U scikit-learn          # 학습 때 버전으로 되돌립니다 (pip list로 비교)
# 컨테이너라면 이미지를 다시 빌드한 뒤 아래로 확인합니다
docker run --rm toxicity-filter:v260429v1 pip list
QUIZ

버전 불일치 경고가 뜨는데 서버도 뜨고 응답도 정상으로 보입니다. 그냥 넘어가도 될까요?

정답 보기
넘어가면 안 됩니다. 지금은 같은 값이 나왔더라도 내부 구조가 달라진 버전 사이에서는 조용히 다른 결과가 나오거나, 특정 입력에서만 오류가 날 수 있습니다. 에러가 아니라 경고라서 놓치기 쉬운 것이 문제이므로, 학습 환경의 버전을 기록해 두고 서빙 환경과 일치하는지 확인하는 단계를 배포 절차에 넣어야 합니다.

09 — HELM

Helm 이해와 설치

쿠버네티스 애플리케이션을 패키지 단위로 설치·관리하는 도구 Helm을 설치합니다.

Helm이란

Helm은 쿠버네티스용 패키지 매니저입니다. apt나 brew가 OS에 프로그램을 설치하는 도구라면, Helm은 쿠버네티스에 애플리케이션을 설치하는 도구입니다. 07장에서는 Deployment와 Service YAML을 직접 썼지만, DB처럼 구성이 복잡한 애플리케이션은 StatefulSet, Service, Secret, PVC 등 YAML이 수십 개 필요합니다. Helm은 이런 YAML 묶음을 차트(chart)라는 패키지로 만들어, 필요한 값만 바꿔 설치하고 업그레이드·롤백까지 할 수 있게 해 줍니다.

용어의미이번 실습에서는
Chart쿠버네티스 YAML 템플릿을 묶은 패키지bitnami/mariadb
Repository차트를 모아 둔 저장소bitnami 저장소
Values템플릿의 빈칸에 넣을 설정값. 기본값이 있고 필요한 것만 덮어씀mariadb-values.yaml
Release차트를 클러스터에 설치한 결과 하나하나에 붙는 이름mariadb

Helm 설치

운영체제에 맞는 방법 하나로 설치합니다. 현재 최신 메이저 버전은 Helm 4이며, 이 교안의 명령은 모두 Helm 4에서 동작합니다.

BASH

# macOS
brew install helm

# Linux · WSL
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-4 | bash

# Windows (PowerShell)
winget install Helm.Helm

# 설치 확인
helm version

OUTPUT (예시)

version.BuildInfo{Version:"v4.3.1", GitCommit:"...", GitTreeState:"clean", GoVersion:"..."}

Helm은 kubectl과 같은 kubeconfig를 사용합니다. 따로 설정하지 않아도 현재 kubectl이 바라보는 클러스터(k3d-mlops)에 설치됩니다.

10 — DATABASE

Helm으로 MariaDB 배포

공개 차트 저장소를 등록하고, 필요한 값만 바꿔 MariaDB를 클러스터에 설치합니다.

차트 저장소 등록

배포용 파일을 모아 둘 deploy 폴더를 만들고 이동한 뒤 진행합니다.

BASH

mkdir -p deploy
cd deploy

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm repo list
helm list -A
  • helm repo add차트 저장소를 bitnami라는 이름으로 등록합니다. 이후 bitnami/차트이름으로 부릅니다.
  • helm repo update등록된 저장소의 최신 차트 목록을 받아옵니다. apt의 apt update와 같은 역할입니다.
  • helm list -A모든 namespace에 설치된 release 목록을 봅니다. 아직 설치한 것이 없으므로 비어 있습니다.

values 파일 작성

차트의 기본값을 먼저 확인합니다. 기본 values는 1,600줄이 넘으므로 파일로 저장해 두고 필요할 때 참고만 합니다.

BASH — 기본값 확인

helm show values bitnami/mariadb > mariadb-values-default.yaml

설치에 쓸 values 파일은 바꿀 값만 담아 새로 만듭니다. 나머지는 차트의 기본값이 그대로 적용됩니다.

mariadb-values.yaml

auth:
  rootPassword: "123mlops"
  database: "toxicity"
  username: "jyjy"
  password: "123mlops"
primary:
  persistence:
    enabled: true
    size: 3Gi
  resources:
    requests:
      cpu: 100m
      memory: 256Mi
    limits:
      cpu: 500m
      memory: 512Mi
  service:
    type: NodePort
    nodePorts:
      mysql: 30082
01

auth

관리자(root) 비밀번호, 처음 만들 데이터베이스 toxicity, 그리고 앱이 쓸 일반 계정 jyjy와 비밀번호입니다. 서빙 코드는 root가 아니라 이 일반 계정으로 접속합니다. 이 값은 DB가 처음 만들어질 때만 적용됩니다(12장 시나리오 1).

02

primary.persistence

DB 데이터를 Pod 밖의 저장 공간(PVC)에 3Gi로 저장합니다. Pod가 재시작되거나 다시 만들어져도 데이터가 남습니다.

03

primary.resources

DB 컨테이너가 보장받는 양(requests)과 최대 상한(limits)입니다. 로컬 실습용으로 작게 잡았습니다.

04

primary.service

Service를 NodePort로 열고 포트를 30082로 고정합니다. 클러스터에 열어 둔 30080–30089 범위 안이라 내 PC에서 localhost:30082로 접속할 수 있습니다.

비밀번호를 평문으로 적어도 되나요? 로컬 실습에서는 괜찮지만, 이 파일을 Git에 올리면 비밀번호가 그대로 노출됩니다. 실무에서는 비밀번호를 쿠버네티스 Secret으로 따로 만들고 values에서는 그 Secret 이름만 참조하는 방식(auth.existingSecret)을 씁니다.

설치와 확인

BASH

helm install mariadb bitnami/mariadb \
  -n database --create-namespace \
  -f mariadb-values.yaml
  • mariadbrelease 이름입니다. 리소스 이름(mariadb, mariadb-0 등)이 이 이름을 따라 만들어집니다.
  • bitnami/mariadb설치할 차트입니다.
  • -n database --create-namespacedatabase namespace에 설치하고, 없으면 만듭니다. 07장에서 k create ns로 직접 만든 것과 같은 효과입니다.
  • -f mariadb-values.yaml기본값 위에 덮어쓸 values 파일입니다.

설치하면 접속 방법을 안내하는 NOTES가 출력됩니다. DB가 완전히 뜨기까지는 30초~1분 정도 걸립니다.

BASH — 배포 확인

k get ns
helm list -n database
k get all -n database
k get pv
k get pvc -n database

OUTPUT (예시) — k get all -n database

NAME            READY   STATUS    RESTARTS   AGE
pod/mariadb-0   1/1     Running   0          60s

NAME                       TYPE        CLUSTER-IP     PORT(S)          AGE
service/mariadb            NodePort    10.43.12.34    3306:30082/TCP   60s
service/mariadb-headless   ClusterIP   None           3306/TCP         60s

NAME                       READY   AGE
statefulset.apps/mariadb   1/1     60s
01

statefulset.apps/mariadb · pod/mariadb-0

서빙은 Deployment였지만 DB는 StatefulSet으로 만들어집니다. StatefulSet의 Pod는 mariadb-0처럼 고정된 이름을 갖고, 다시 만들어져도 같은 저장 공간(PVC)에 다시 연결됩니다. 데이터를 가진 애플리케이션에 쓰는 방식입니다.

02

service/mariadb · 3306:30082

클러스터 안에서는 3306, 내 PC에서는 30082로 접속합니다. 나중에 서빙 Pod는 클러스터 안에서 mariadb.database(서비스이름.namespace) 주소의 3306 포트로 DB에 접속합니다.

03

k get pv · k get pvc

PVC(data-mariadb-0)는 “3Gi 저장 공간이 필요하다”는 요청이고, PV는 실제로 할당된 저장 공간입니다. k3d에는 기본 저장소(local-path)가 있어서 PVC를 만들면 PV가 자동으로 생깁니다. 데이터는 노드 컨테이너 안에 저장되므로, 클러스터를 삭제하면 함께 사라집니다.

QUIZ

values 파일에 적은 비밀번호는 클러스터 안 어디에 저장될까요? 그리고 그 값은 암호화되어 있을까요?

정답 보기
차트가 만든 Secret(mariadb)에 저장됩니다. Secret의 값은 base64로 인코딩만 되어 있을 뿐 암호화된 것이 아니어서, 권한만 있으면 누구나 원래 값을 볼 수 있습니다.
k get secret mariadb -n database -o jsonpath='{.data.mariadb-password}' | base64 -d

업그레이드와 롤백

Helm은 설치 이력을 버전(revision)으로 남깁니다. values를 바꿔 다시 적용하고, 문제가 있으면 이전 revision으로 되돌릴 수 있습니다.

BASH

# mariadb-values.yaml에서 limits.memory를 768Mi로 바꾼 뒤
helm upgrade mariadb bitnami/mariadb -n database -f mariadb-values.yaml
helm history mariadb -n database

# 이전 revision으로 되돌리기
helm rollback mariadb 1 -n database
helm history mariadb -n database

helm history에 revision 1(install), 2(upgrade), 3(rollback)이 차례로 쌓입니다. 롤백도 새 revision으로 기록된다는 점이 07장의 k rollout undo와 비슷합니다.

upgrade할 때도 같은 -f 파일을 함께 주세요. --set 등으로 바꿀 값 하나만 넘기면, 앞서 values 파일로 지정했던 나머지 값이 차트 기본값으로 돌아갈 수 있습니다. 설치·업그레이드 모두 같은 values 파일을 고쳐서 쓰는 습관이 안전합니다.

③ mariadb-0:30082

정답 보기
정답 ② — 서빙 Pod 입장에서 localhost는 자기 자신입니다. 클러스터 안에서는 Service 이름으로 접속하고, 다른 namespace에 있으므로 서비스이름.namespace 형태(mariadb.database)로 씁니다. 포트는 NodePort(30082)가 아니라 Service 포트(3306)입니다. NodePort는 클러스터 밖에서 들어올 때 쓰는 문입니다.

12 — TROUBLESHOOTING

DB 장애 재현 실습

Helm으로 배포한 DB에서 자주 마주치는 문제를 재현하고 해결해 봅니다.

시나리오 1 — 재설치했는데 새 비밀번호로 접속이 안 됨

실무에서는 비밀번호를 바꾸려고 values만 고친 뒤 재설치하거나 업그레이드했을 때 자주 겪습니다. “분명히 비밀번호를 바꿨는데 접속이 안 된다”는 문의의 상당수가 이 경우입니다.

BASH — 재현

helm uninstall mariadb -n database
k get pvc -n database                  # PVC가 그대로 남아 있습니다

# mariadb-values.yaml의 auth.password를 "newpass123"으로 바꾼 뒤
helm install mariadb bitnami/mariadb -n database -f mariadb-values.yaml

# DBeaver에서 새 비밀번호(newpass123)로 Test Connection

Pod는 정상적으로 Running인데 새 비밀번호로는 Access denied for user 'jyjy' 오류가 나고, 오히려 옛 비밀번호로 접속됩니다. helm uninstall은 StatefulSet이 만든 PVC를 지우지 않으므로 기존 데이터가 남아 있고, 비밀번호 같은 auth 값은 DB를 처음 초기화할 때만 적용되기 때문입니다. 데이터가 이미 있으면 초기화를 건너뜁니다.

BASH — 해결 (실습용: 데이터를 지우고 처음부터)

helm uninstall mariadb -n database
k delete pvc data-mariadb-0 -n database
helm install mariadb bitnami/mariadb -n database -f mariadb-values.yaml

PVC를 지우면 DB 데이터도 모두 사라집니다. 실무에서는 데이터를 지우지 않고, DB에 접속해 ALTER USER로 비밀번호를 바꾼 뒤 Secret과 values를 함께 맞춥니다. 실습이 끝나면 비밀번호를 원래 값(123mlops)으로 되돌려 둡니다.

QUIZ

helm uninstall이 PVC를 자동으로 지우지 않는 이유는 무엇일까요?

정답 보기
DB 데이터를 실수로 날리지 않기 위해서입니다. 애플리케이션은 언제든 다시 설치할 수 있지만 데이터는 한 번 지우면 되돌릴 수 없습니다. 그래서 쿠버네티스는 StatefulSet이 만든 PVC를 사람이 명시적으로 지울 때까지 남겨 둡니다.

시나리오 2 — NodePort 충돌

실무에서는 여러 사람이 같은 클러스터를 쓰면서 각자 NodePort 번호를 고정할 때 발생합니다. 포트 번호를 정리해 둔 문서 없이 쓰다 보면 언젠가 반드시 겹칩니다.

BASH — 재현

# mariadb-values.yaml의 nodePorts.mysql을 서빙과 같은 30089로 바꾼 뒤
helm upgrade mariadb bitnami/mariadb -n database -f mariadb-values.yaml

업그레이드가 실패하고 provided port is already allocated라는 메시지가 나옵니다. NodePort 번호는 namespace와 상관없이 클러스터 전체에서 하나만 쓸 수 있으므로, serving namespace의 서빙 Service가 이미 쓰고 있는 30089는 할당되지 않습니다.

BASH — 원인 확인과 해결

k get svc -A | grep 300            # 어떤 Service가 어떤 NodePort를 쓰는지 확인
# nodePorts.mysql을 30082로 되돌린 뒤
helm upgrade mariadb bitnami/mariadb -n database -f mariadb-values.yaml

시나리오 3 — DB 이미지를 받지 못함

실무에서는 외부에서 제공하는 이미지·차트의 배포 정책이 바뀌면, 내 코드는 그대로인데 어느 날 갑자기 설치가 실패합니다. 실제로 Bitnami는 2025년 8월부터 무료 이미지 정책을 바꿔, 버전이 붙은 기존 이미지를 bitnamilegacy라는 별도 저장소로 옮겼습니다. 이미 받아 둔 이미지가 있는 노드에서는 잘 되다가, 새 클러스터에서만 실패하는 식으로 나타나 원인을 찾기 어렵습니다.

BASH — 증상 확인

k get pods -n database                 # STATUS: ErrImagePull 또는 ImagePullBackOff
k describe pod mariadb-0 -n database   # Events에서 not found / manifest unknown 확인

이 증상이 나오면 values에 이미지 저장소를 바꾸는 설정을 추가하고 업그레이드합니다.

mariadb-values.yaml에 추가

image:
  repository: bitnamilegacy/mariadb
global:
  security:
    allowInsecureImages: true

BASH — 해결

helm upgrade mariadb bitnami/mariadb -n database -f mariadb-values.yaml
k get pods -n database -w

13 — SCHEMA

테이블 만들기

예측 결과와 사용자 피드백을 저장할 두 테이블을 설계하고 만듭니다.

테이블 설계

predictions PREDICTION LOG

모델이 예측할 때마다 한 줄씩 쌓이는 기록

  • 입력 문장, 판정(0/1), 확률
  • 그때 쓴 임계값과 모델 이름·alias
  • 나중에 “어떤 모델이 무엇을 어떻게 판정했나”를 추적

feedback HUMAN LABEL

사용자나 관리자가 알려 준 실제 정답

  • 어떤 예측에 대한 피드백인지(prediction_id)
  • 실제 정답(true_label)
  • 예측 하나당 피드백은 한 번만

테이블 생성

11장에서 만든 DBeaver 연결(toxicity DB)에서 SQL 편집기를 열고, 아래 SQL 전체를 붙여 넣은 뒤 스크립트 실행(Alt+X)으로 한 번에 실행합니다.

schema.sql

CREATE TABLE IF NOT EXISTS predictions (
  id CHAR(36) PRIMARY KEY,          # 예측 고유 ID
  text TEXT NOT NULL,               # 사용자 텍스트 원문
  pred_label TINYINT NOT NULL,      # 모델이 내린 이진 판정(0=정상, 1=유해)
  pred_proba FLOAT NOT NULL,        # 모델이 예측한 “유해 확률”(0~1)
  threshold FLOAT NOT NULL,         # 당시 판정에 사용한 임계값(예: 0.5)
  model_name VARCHAR(100) NOT NULL, # 모델 이름 (MLflow 연동 전: toxicity-filter)
  model_alias VARCHAR(50) NOT NULL, # 모델 alias (MLflow 연동 전: local)
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_created_at (created_at)
);

CREATE TABLE IF NOT EXISTS feedback (
  id CHAR(36) PRIMARY KEY,          # 피드백 고유 ID
  prediction_id CHAR(36) NOT NULL,  # 어떤 예측에 대한 피드백인지
  true_label TINYINT NOT NULL,      # 사용자/관리자가 판단한 정답(0=정상, 1=유해)
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_feedback_prediction # 예측이 삭제되면 해당 피드백도 같이 삭제
    FOREIGN KEY (prediction_id) REFERENCES predictions(id)
    ON DELETE CASCADE,
  UNIQUE KEY uq_feedback_prediction (prediction_id), # 예측 하나당 피드백은 한 번만
  INDEX idx_created_at (created_at)
);
01

id CHAR(36) PRIMARY KEY

UUID(71902efb-5ae2-… 같은 36자 문자열)를 기본키로 씁니다. 번호를 DB가 매기지 않고 서빙 코드가 직접 만들어 넣습니다.

02

FOREIGN KEY ... ON DELETE CASCADE

피드백의 prediction_id는 반드시 실제로 있는 예측의 id여야 합니다. 예측이 삭제되면 그 예측에 달린 피드백도 자동으로 함께 삭제됩니다.

03

UNIQUE KEY uq_feedback_prediction (prediction_id)

같은 prediction_id가 feedback 테이블에 두 번 들어갈 수 없게 합니다. “예측 하나당 피드백은 한 번”이라는 규칙을 DB가 직접 지켜 줍니다. UNIQUE 제약은 인덱스 역할도 같이 합니다.

04

INDEX idx_created_at (created_at)

“최근 일주일 예측”처럼 시간으로 자주 조회할 컬럼에 인덱스를 걸어 조회를 빠르게 합니다.

SQL — 생성 확인

SHOW TABLES;
DESC predictions;
DESC feedback;
QUIZ

예측 ID를 DB의 자동 증가 번호(AUTO_INCREMENT) 대신 서빙 코드에서 UUID로 만드는 장점은 무엇일까요?

정답 보기
DB에 저장하기 전에 ID를 알 수 있어서, 저장과 동시에 그 ID를 응답으로 돌려주기 쉽습니다. 또 서빙 Pod가 여러 개여도 서로 겹치지 않는 ID를 각자 만들 수 있고, 1, 2, 3처럼 순서가 드러나지 않아 다른 사람의 예측 ID를 추측하기 어렵습니다.

get_conn()

05

16 — CONFIG & DEPLOY

ConfigMap · Secret으로 배포

DB 접속 정보를 코드와 이미지 밖에서 넣어 주고, 클러스터에 배포한 뒤 헬스체크(probe)를 추가합니다.

ConfigMap과 Secret

로컬에서는 코드의 기본값(127.0.0.1:30082)으로 DB에 붙었지만, 클러스터 안의 Pod에서 127.0.0.1은 Pod 자기 자신입니다. 그래서 Pod에는 클러스터 안의 DB 주소를 알려 줘야 합니다. 이런 값을 이미지에 넣어 버리면 환경이 바뀔 때마다 다시 빌드해야 하므로, 쿠버네티스 리소스로 따로 관리하고 컨테이너가 시작될 때 환경변수로 주입합니다.

ConfigMap CONFIGURATION

일반 설정값을 담는 리소스

  • DB 주소, 포트, DB 이름
  • 모델 이름, alias
  • 값이 그대로 보여도 괜찮은 정보

Secret SENSITIVE DATA

민감한 값을 담는 리소스

  • DB 사용자 이름, 비밀번호, API 키 등
  • 조회 권한을 따로 제한할 수 있음
  • base64 인코딩일 뿐 암호화는 아님(10장 퀴즈)

비밀번호를 Deployment YAML에 평문으로 적지 않고 Secret으로 빼면 다음과 같은 장점이 있습니다.

01

실수로 유출될 확률 감소

Deployment YAML에 평문으로 있으면 Git 커밋, 공유, 로그, 코드 리뷰 과정에서 그대로 노출됩니다. Secret으로 빼면 매니페스트 파일에는 값이 아니라 Secret 이름(참조)만 남습니다.

02

권한 분리(Access Control)

쿠버네티스 RBAC로 누가 Secret을 읽을 수 있는지 제한할 수 있습니다. 다만 Secret은 기본적으로 암호화가 아니라 base64 인코딩이라, 접근 권한이 뚫리면 읽힐 수 있습니다. 그래도 노출될 수 있는 범위를 크게 줄여 줍니다.

03

운영 편의

같은 이미지와 Deployment를 쓰면서 환경(dev/stg/prod)별로 Secret만 바꿔 끼울 수 있습니다. 비밀번호를 교체할 때도 Deployment YAML은 그대로 두고 Secret만 바꾸면 됩니다. 단, 바뀐 값을 읽으려면 보통 Pod를 다시 시작해야 합니다(17장 시나리오 3).

04

도구 연동이 쉬움

sealed-secrets, External Secrets Operator, Vault 같은 비밀 관리 도구로 확장할 때 쿠버네티스 Secret이 표준 출발점입니다.

공식 문서 — 더 자세한 내용은 쿠버네티스 공식 문서의 Secret, ConfigMap 항목을 참고하세요.

Probe 추가

지금은 컨테이너가 실행되기만 하면 쿠버네티스가 “준비됐다”고 판단합니다. 08장 시나리오 2에서 본 것처럼, 이러면 아직 준비가 안 됐거나 곧 죽을 Pod에도 요청이 갈 수 있습니다. 쿠버네티스가 /healthz를 주기적으로 호출해 상태를 확인하도록 probe를 추가합니다.

Probe실패하면왜 필요한가
Readiness
준비됐을 때만 트래픽 받기		Service 대상에서 제외. 요청은 다른 Pod로 가고, 받을 Pod가 하나도 없으면 접속 자체가 실패모델 로딩처럼 준비가 끝나기 전에 요청을 받으면 장애처럼 보입니다. 배포·재시작 중 잠깐의 실패를 줄입니다
Liveness
죽었으면 자동 재시작		kubelet이 컨테이너를 재시작프로세스는 떠 있지만 데드락·무한 대기로 일을 못 하는 상태(hang)는 쿠버네티스가 스스로 알아채지 못합니다
Startup (선택)
초기 기동이 느린 앱 보호		정해진 횟수 안에 성공하지 못하면 재시작모델 다운로드·로딩으로 처음 뜨는 데 오래 걸리면 liveness가 “죽었다”고 오판해 재시작 루프에 빠질 수 있습니다. startup이 성공하기 전까지는 나머지 판정을 미룹니다

serving.yaml의 컨테이너 설정에 아래 probe 세 개를 추가합니다. envFrom 바로 아래, 같은 들여쓰기에 넣습니다.

serving.yaml — probe 추가

apiVersion: apps/v1
kind: Deployment
metadata:
  name: toxicity-filter
  namespace: serving
spec:
  replicas: 1
  selector:
    matchLabels:
      app: toxicity-filter
  template:
    metadata:
      labels:
        app: toxicity-filter
    spec:
      containers:
        - name: app
          image: toxicity-filter:v260429v3
          imagePullPolicy: Never
          ports:
            - containerPort: 8088
          envFrom:
            - configMapRef:
                name: tf-config
            - secretRef:
                name: tf-secrets
          # 컨테이너가 "기동 중"인 동안 너무 빨리 죽었다고 판단하지 않도록 보호(선택)
          startupProbe:
            httpGet:
              path: /healthz
              port: 8088
            failureThreshold: 30
            periodSeconds: 2
          # 트래픽 받을 준비가 됐는지(준비 전이면 Service에서 제외)
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8088
            initialDelaySeconds: 2
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          # 프로세스가 "살아있는지"(죽거나 응답 불능이면 재시작)
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8088
            initialDelaySeconds: 10
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
---
apiVersion: v1
kind: Service
metadata:
  name: toxicity-filter
  namespace: serving
spec:
  type: NodePort
  selector:
    app: toxicity-filter
  ports:
    - name: http
      port: 8088
      targetPort: 8088
      nodePort: 30089
  • failureThreshold: 30 · periodSeconds: 2startup은 2초마다 최대 30번, 약 60초까지 기다려 줍니다.
  • initialDelaySeconds첫 검사를 시작하기 전에 기다리는 시간입니다.
  • timeoutSeconds: 22초 안에 응답이 없으면 그 회차는 실패로 봅니다.
  • failureThreshold: 33번 연속 실패해야 “실패”로 판정합니다. 한 번의 일시적인 지연으로 재시작되는 것을 막습니다.

k rollout status deployment/toxicity-filter -n serving
k describe pod -l app=toxicity-filter -n serving | grep -E "Liveness|Readiness|Startup"

지금의 /healthz가 확인하는 범위. 이 앱은 모델 로드가 끝나야 포트가 열리므로 /healthz가 응답한다는 것은 모델이 준비됐다는 뜻입니다. 하지만 DB나 MLflow 연결은 확인하지 않습니다. 그래서 DB 주소가 틀려도 probe는 모두 통과합니다(17장 시나리오 3). DB 연결까지 readiness에 반영하려면 별도 엔드포인트가 필요한데, 이것을 liveness에 쓰면 안 되는 이유는 17장 퀴즈에서 다룹니다.

17 — TROUBLESHOOTING

연동 장애 재현 실습

서빙과 DB가 연결되면서 새로 생기는 문제들을 재현하고 해결해 봅니다.

시나리오 1 — 테이블이 없음

실무에서는 새 환경(개발 → 운영)에 애플리케이션만 배포하고 테이블 생성(마이그레이션)을 빼먹었을 때, 또는 테이블 이름을 바꾸는 작업과 코드 배포의 순서가 어긋났을 때 발생합니다.

SQL — 재현 (DBeaver)

RENAME TABLE predictions TO predictions_bak;

이 상태에서 /predict를 호출하면 500 오류가 나고, k logs deploy/toxicity-filter -n serving에 pymysql.err.ProgrammingError: (1146, "Table 'toxicity.predictions' doesn't exist")가 남습니다. 테이블 이름만 바꾼 것이라 데이터는 그대로 있습니다.

SQL — 해결

RENAME TABLE predictions_bak TO predictions;

feedback 테이블의 외래키는 테이블 이름이 바뀔 때 자동으로 따라가므로, 이름을 되돌리면 원래대로 동작합니다.

시나리오 2 — ConfigMap이 없어 Pod가 뜨지 않음

실무에서는 새 namespace나 새 클러스터에 Deployment만 옮기고 ConfigMap·Secret을 같이 옮기지 않았을 때, 또는 이름을 오타 냈을 때 발생합니다.

BASH — 재현

k delete configmap tf-config -n serving
k rollout restart deployment/toxicity-filter -n serving
k get pods -n serving
k describe pod <새로 생긴 Pod 이름> -n serving

새 Pod의 STATUS가 CreateContainerConfigError로 멈추고, Events에 configmap "tf-config" not found가 보입니다. 컨테이너가 아예 시작되지 못했으므로 Ready가 될 수 없고, 기존 Pod가 계속 요청을 받습니다.

BASH — 해결

k apply -f configmap.yaml
k get pods -n serving -w

ConfigMap이 다시 생기면 쿠버네티스가 컨테이너 생성을 다시 시도해 자동으로 Running이 됩니다.

시나리오 3 — ConfigMap을 고쳤는데 반영되지 않음

실무에서는 DB 주소가 바뀌어 ConfigMap을 수정했는데 애플리케이션이 계속 옛 주소로 접속하거나, 반대로 아무도 모르게 잘못된 값이 들어가 있다가 Pod가 재시작되는 순간 장애가 나는 경우가 있습니다.

BASH — 재현

# DB_HOST를 잘못된 값으로 바꿉니다

QUIZ

그렇다면 /healthz에서 DB 연결까지 확인하도록 바꾸고, 그것을 livenessProbe에 쓰면 될까요?

정답 보기
livenessProbe에 쓰는 것은 위험합니다. DB가 잠깐 끊기면 서빙 Pod가 전부 “죽었다”고 판단되어 계속 재시작되고, DB가 돌아와도 한동안 서비스가 불안정해집니다. 서빙 Pod를 재시작해도 DB 문제는 해결되지 않습니다. DB 확인은 readinessProbe용 엔드포인트를 따로 두어 “지금은 요청을 받지 말라”는 신호로만 쓰고, livenessProbe는 프로세스 자체가 살아 있는지만 보게 하는 것이 일반적입니다.
