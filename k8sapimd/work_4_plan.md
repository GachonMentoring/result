## 3. 배포 방식 비교

```
① 한 컨테이너         ② 사이드카 (같은 파드)             ③ 별도 2개 파드
┌──────────────┐     ┌──────────── Pod ────────────┐    ┌── Pod ──┐  Service  ┌── Pod ──┐
│ server       │     │ server ──localhost──▶ model │    │ server  │ ────────▶ │ model   │
│  + 모델 로드  │     │ (컨테이너 A)     (컨테이너 B)│    └─────────┘           └─────────┘
└──────────────┘     └─────────────────────────────┘
```

| 기준 | ① 한 컨테이너 | ② 사이드카 | ③ 별도 파드 |
|---|---|---|---|
| server/·model/ 분리 | ✕ (한 이미지) | ✅ 이미지 2개 | ✅ 이미지 2개 |
| 통신 | 함수 호출 | `localhost` (Service 불필요, 지연 최소) | Service DNS (`toxicity-filter.mentor:8088`) |
| 의존성 분리 (sklearn ↔ kubernetes) | ✕ 섞임 | ✅ | ✅ |
| 모델만 교체 (재학습 후) | 서버 이미지 재빌드 | **파드 전체 롤아웃 (서버도 재시작)** | **모델 파드만 롤아웃** |
| 스케일 | 함께 | **함께** (replicas 공유) | 각자 |
| 권한(ServiceAccount 토큰) | — | **모델 컨테이너에도 플랫폼 SA 토큰이 마운트됨** → 막으려면 수동 설정 필요 | 모델 파드는 권한 없음 |
| base.md 구조 (서비스 Workload ↔ 플랫폼) | 섞임 | **섞임** — 플랫폼 파드 안에 워크로드가 들어감 | ✅ 분리 — 플랫폼이 모델 파드를 "관리 대상"으로 보여줌 |
| 셀프힐링·재시작 시연 | — | 모델 파드를 지우면 플랫폼도 같이 죽음 | 모델 파드 삭제·재시작을 플랫폼 화면에서 시연 가능 |
| 매니페스트 수 | 적음 | 적음 | Deployment·Service 1벌 추가 (이미 존재) |

### 검토 의견

- **사이드카가 잘 맞는 경우**: 앱 서버가 "댓글 서비스 전용"이고 모델과 항상 같이 움직일 때 (가이드의 `app.py` 역할만 하는 서버).
- **우리 상황**: `server/`는 이미 **쿠버네티스를 관리하는 플랫폼 서버**(Watch·삭제·재시작·매니페스트 apply 권한)입니다. 여기에 모델을 사이드카로 붙이면
  1. 모델 교체 = 플랫폼 서버 재시작 (Watch 캐시 재동기화, 화면 끊김)
  2. 모델 컨테이너가 플랫폼의 강한 권한 토큰을 함께 받음
  3. base.md의 "플랫폼이 서비스(워크로드)를 관리·시연" 구조가 흐려짐 — 인프라 화면에서 모델 파드를 지우는 시연이 곧 플랫폼 자신을 지우는 일이 됨
- **변형안 (②')**: 사이드카를 쓰되 **댓글 서비스 전용 파드** `[comment-api + model]`를 플랫폼 파드와 따로 두는 방식 — 사이드카의 장점과 플랫폼 분리를 둘 다 얻지만 서버가 3종류가 됨.
- **중요**: 어느 방식이든 앱 코드는 `MODEL_URL` 환경변수 하나로 모델을 부르게 만들면 **코드는 같고 배포 매니페스트만 달라집니다.**
  ② → `http://localhost:8089`, ③ → `http://toxicity-filter.mentor:8088`, 개발 → `http://192.168.2.20:30089` 또는 로컬 모델 서버.
  → Work 4 구현은 방식 확정 전에도 진행 가능, 배포 Work에서 매니페스트로 결정해도 됨.

## 4. 설계안

### 4-1. `model/` (모델 서버 — 추론만 담당, DB 없음)

```
model/
├─ train.py            가이드 02장 그대로 (char (3,6), min_df 2, LogisticRegression) + 메타데이터 기록
├─ data/seed.csv       가이드 HTML에서 추출 (458행)
├─ serve.py            FastAPI: GET /healthz, GET /info, POST /predict  (가이드 app.py 05장 기반)
├─ requirements.txt    버전 고정 (scikit-learn==1.9.1 등 — 가이드 08장 시나리오 3 방지)
├─ Dockerfile          python:3.11-slim, 모델을 이미지에 포함 (가이드 06장)
└─ artifacts/          model.joblib, metrics.json (빌드 산출물)
```
- `/predict` → `{toxic_proba, label}` (label은 기본 0.5 기준, 참고용)
- `/info` → 모델 이름·버전(이미지 태그/학습 시각)·scikit-learn 버전·학습 지표 → 화면에 "어떤 모델이 판정했는지" 표시, Work 5에서 DB `model_name/model_alias` 로 기록
- 포트: ② 사이드카면 기존 8088과 겹치지 않게 **8089** (플랫폼 서버 8000)

### 4-2. `server/` (앱 서버 — 입력 검증, 모델 호출, Work 5에서 DB)

| Method | Path | 설명 |
|---|---|---|
| POST | `/api/v1/comments/predict` | `{text}` → 검증(1~300자, 공백만 불가) → 모델 호출 → `{label, toxic_proba, threshold, model, latency_ms}` |
| GET | `/api/v1/comments/model` | 모델 서버 상태 + `/info` (화면 상단 표시용) |

- `MODEL_URL`, `THRESHOLD`(기본 0.5) 환경변수. **판정(임계값 적용)은 앱 서버에서** → Work 5에서 DB에 threshold 와 함께 기록하기 좋음
- 모델 호출: `httpx` 타임아웃 3초, 모델 다운/타임아웃 → **503** "모델 서버에 연결할 수 없습니다", 모델 4xx → 그대로 전달
- `/readyz` 는 지금처럼 Watch 동기화만 봄 (모델 장애가 플랫폼 readiness 를 떨어뜨리지 않게 — 가이드 17장 퀴즈 원칙)

### 4-3. 화면 — 좌측 메뉴 "댓글 기능"

```
┌ 댓글 분류 ─────────────────────────── 모델 toxicity-filter · sklearn 1.9.1 ● 연결됨 ┐
```

- 테스트 14개 추가 → 서버 전체 70개 통과

### front/ — 댓글 기능 화면
- 입력창(300자 카운터, Ctrl+Enter), 예시 문장 5개, 결과 카드(정상/주의, 확률 막대 + 임계값 선, 0.4~0.6 경계 안내, 모델 버전·응답 시간), 이번 화면 기록 20개
