### 목표 : MLOps와 Kubernetes를 이용해서 학과 과정에서는 채득이 힘든 운영과정 경험

여기서 작년 팀 자료를 공부해본 결과 Kubernetes에 대한 부분이 붕 뜬다고 생각이 들었습니다. 이 부분이 개선되면 더 좋은 성과발표를 할 수 있을 거라고 생각이 들었습니다.

**→ Kubernetes를 왜 쓰는가?** 에 대한 저희의 작지만 의미있는 결론을 보여주는 것이 단순히 ~해봤다. 보다 더 도움되는 산출물을 낼 수 있을 거라고 생각했습니다. AI 인프라 생태계에서 k8s가 표준이 된 것에는 많은 이유가 있다고 생각이 들지만, GPU 자원이나 대규모 시스템에 따른 재해복구 네트워킹 오토스케일링 등은 해당 **성과발표** 내에서 어필하기 힘들다고 생각이 되었습니다. 

→ **중앙 집중적 선언형 관리 (리소스 관리의 편리성)**

그래서 k8s의 여러 특성 중에서 선언형 관리 쪽에 포커싱을 맞추는 게 어떨까 생각이 들었습니다. 쿠버네티스는 미리 작성해둔 spec 에 맞춰 인프라 상태를 계속 유지하려는 특성이 핵심 특성 중 하나기 때문에 이 부분을 리소스 관리와 묶어서 어필 해보는 것이 어떨까 생각이 들었습니다.

여기서 어필하고자 하는 쿠버네티스의 지속/선언 관리의 포인트는 

사용자가 원하는 인프라 상태를 yaml로 정의 → Kube-Controller가 현재 상태와 원하는 상태의 차이를 지속 관리 → 리소스가 선언한 상태를 벗어나면 셀프-힐링 → 그리고 이러한 상태를 처음의 yaml을 통해서 명세화해서 일관된 형태로 관리하는 전체 : 즉, 쿠버네티스는 **인프라를 코드로 정의하고, 선언한 상태를 지속적으로 유지할 수 있다** 라는 것을 이해하고 실행으로 옮겨 보는 것입니다.

**→ 결론 : 간단한 댓글 분류 서비스의 플랫폼을 만들어보자(AI 모델을 운영하기 위한 인프라의 상태와 변경 이력을 관리하는 미니 운영 플랫폼)**

**서비스 (Workload)**

기존의 댓글 독성 분류 모델을 서빙해서 댓글을 입력하면 DB로 트랜잭션을 수행하고 모델이 추론을 실행해서 분류결과를 리턴하고 트랜잭션을 수행하는 간단한 API 서버 및 웹을 개발합니다. 

**플랫폼**

1. 추론 결과 데이터 시각화
2. Job을 통한 데이터셋 생성 및 모델 재학습
3. 인프라 관리 기능  (pod/job/svc/db 등..) 
4. 모니터링 → 모델 / 서버 (시간남으면)

상세히

1. 추론 결과 데이터 시각화는 1학기 팀에서도 수행했던 API 서버 기능입니다. 
2. 충분한 데이터셋이 다시 누적되면 모델을 재학습할 필요가 있습니다. 이것을 플랫폼에서 API 호출과 Job 을 통해 수행할 수 있게 합니다. 모델 교체까지는 생각을 해보겠습니다.
3. Job을 포함한 리소스 관리 화면 → k8s 렌즈 같은 느낌으로 간단하게 구현하는 것으로 생각 → 해당 기능을 통해 인프라 리소스의 상태를 시각화하고 매니페스트를 확인 및 관리하고, 중앙 관리식으로 하여 바로 적용 교체하고 상태가 일치하는지 점검할 수 있는 시각화의 구현
4. 프로메테우스 그라파나를 이용한 모니터링
